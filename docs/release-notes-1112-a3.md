## 1.11.2-a3

Второе исправление обновления: когда GitHub API отвечает отказом, приложение падало с «HTTP 404».

- **Что было не так.** Проверка обновлений сначала спрашивает GitHub API, а при отказе (лимит 60 запросов в час на адрес, общий для всех за одним NAT) переходит на публичную ленту релизов `releases.atom`. В ленте заголовок записи — это *имя* релиза, а не тег, а у релизов этого форка имя идёт без префикса `v`, тогда как тег — с ним. Приложение подставляло имя вместо тега и просило `releases/download/1.11.2-a2/…` вместо `releases/download/v1.11.2-a2/…`; GitHub отвечал 404, и в диалоге появлялось «Не удалось скачать: HTTP 404 while downloading TgWsProxy-…-android.apk». Резервный путь был сломан для всех релизов форка с самого начала.
- **Что исправлено.** Тег берётся из ссылки записи ленты (`/releases/tag/<тег>`), а не из заголовка, поэтому резервный путь скачивает тот же файл, что и обычный.
- **Дополнительная проверка.** Перед передачей установщику скачанный файл проверяется: он должен разбираться как APK, быть тем же пакетом и иметь версию новее установленной. В резервном пути GitHub не отдаёт хеш файла, и раньше повреждённая загрузка доходила до установщика, который отвечал сухим «Приложение не установлено»; теперь такой файл удаляется, а в диалоге видно понятную причину.
- **Ссылка-подключение, ядро и настройки не менялись.** Ядро `1.11.2`, как в `1.11.2-a2`.
- **Проверено на эмуляторе.** Лимит GitHub API был исчерпан намеренно, чтобы приложение проверяло обновления именно через ленту релизов: с установленной `1.11.2-a3` оно нашло, скачало и установило следующую сборку системным установщиком — без ошибок 404 (это была проверочная `1.11.2-a4`, versionCode 20; после проверки она удалена, актуальная версия — `1.11.2-a3`). Заодно сработала и новая проверка скачанного файла: версия в нём должна быть новее установленной.

Пакет `com.nixikon.tgwsproxy`, версия `1.11.2-a3` (versionCode 19), ABI `arm64-v8a` + `x86_64`.

Обновление ставится поверх `1.11.1-a1`, `1.11.2-a1` и `1.11.2-a2`.
